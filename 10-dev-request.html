Handoff to dev

Development request

The deliverable. What the package contains and why it is laid out that way, what blocks a send versus what only warns, how it reaches GitLab, and how development status is tracked afterwards.

Package: com.bizplay.builder.devrequest (59 files) Canonical design: docs/superpowers/specs/2026-08-22-dev-request-package-design.md Screens: artifacts/dev-requests.html, artifacts/dev-request.html, fragments/dev-delivery-progress.html

⭐ This is the contract with development. The test for any decision here is not "is it tidy" but "is there a blank field that we will argue about later".

A package, not a document#

A development request (DR-) is created automatically from a completed FRD or an SRT. There is no screen for writing an empty one by hand. It snapshots the requirements and the work results as they were at that moment.

DR-003/
├─ dev-request.md
├─ expected-back.md
├─ manifest.json
├─ attachments/
│  └─ <files the planner attached>
└─ screens/
   └─ <system>/
      ├─ assets/                  one set of css · js · images
      └─ <screenId>/
         ├─ as-is.html   to-be.html
         ├─ as-is.md     to-be.md
         └─ changes.md

Why there is a system layer#

Mockups are extracted from production, so they depend on ../assets/css/style.css. Moving them to a flat screens/<screenId>/ breaks every style when development opens them.

One system layer makes screens/<system>/<screenId>/to-be.html's ../assets/... resolve to screens/<system>/assets/... on its own — without editing one character inside the file.

  • ⛔ Do not use a single screens/assets/. One FRD can touch screens in two systems (FrdScreen.systemCode is per screen) and the assets would collide.
  • ⛔ Do not select a skin — pour in the whole core/<system>/assets/ (the 2026-08-24 implementation reversed the original decision). Selecting would require rewriting links, and SkinRewriter's own contract is "never modify the stored copy; substitute only in the response". More importantly, selecting code must hold skin folder names — not selecting deletes that question entirely, so iks/tnj-shaped strings never enter the code. manifest.json records where the assets came from (assetRoots), not what was chosen.

Every name is ASCII#

Screen folders are screen IDs (wv-card-list); the human-readable screen name lives inside the MD.

⛔ No Korean folder or file names. They used to be 개발요청서.md / 변경내용.md, relying on java.util.zip's UTF-8 name plus the language-encoding bit — and that code's own comment admitted it could break in older tools. After receiving a real package the risk was removed. Nothing in the package has a Korean name now, and section 8 keeps the meaning by describing each file in one line.

Four files per screen#

File What Why
as-is.html · as-is.mdThe before side of the completion commit⭐ The contract is "from what → to what". Given only to-be, development has to derive the diff itself, and later there is no basis to settle "it was always like that / no it wasn't". It is nearly free — the worktree already has it
to-be.htmlThe after sideWhat it should look like
to-be.mdGenerated by AI before sendingKeeps the contract's field from being blank
changes.mdThat screen's change listCarries what the mockup cannot say — reasons and cautions

⛔ Do not put "the FRD document" in a screen folder. There is one FRD per work item, so per-screen copies would be N duplicates that drift. The FRD body lives in dev-request.md.

to-be.md is generated before sending#

Only screens the canvas AI touched have a frd_screen_history.md; mockup-only screens have null, which would leave the "feature definition to be changed" field mostly empty.

So the AI writes it before sending, from three materials already in hand: as-is.md, the mockup before/after, and that screen's change list.

  • ⚠ A screen that already has an MD keeps it. What a human made through conversation is stronger and is never overwritten.
  • ⭐ FRD completion triggers it by itself (confirmed 2026-08-25) — at that moment the mockup is committed and all three materials are fixed. The user is not made to hunt for a button; the button remains only for re-running a failed screen. Completion still succeeds if it cannot be triggered, but a missing feature definition blocks sending.
  • ⚠ A simple-change FRD with no workbench has no frd_screen_history and therefore no material — empty is correct there.
  • ⛔ Do not go back to "always write the MD during screen work": it makes screen work heavy and forces an MD re-match on every edit, which increases the places where mockup and MD diverge.

dev-request.md — eleven sections#

The body is a regenerated artifact. The AI writes it; humans do not hand-edit it. So each section's material is pinned down. ⛔ Never create a section with no material — the AI will invent something to fill it.

Section 4 is the heart of the contract. Disputes come less from "done / not done" than from "this was in scope / it wasn't". OPERATE and OUTSIDE are already separated, with the reason in note.

⛔ Do not copy the screen's layout into the MD — on dev-request.html this sits small in an <aside>; in the MD it is a large section immediately after the development scope.

⛔ Section 8 is never hand-written — it is generated from the file list in manifest.json. Hand-writing it lets it drift from the screens/ folder, and once drifted nobody knows which is right. That is exactly where "12 artifacts vs 14" split.

⛔ Do not re-expand per-screen changes in the MD. The detail's source of truth is screens/<system>/<screenId>/changes.md; section 8 is an index only.

No README in the package#

Considered and rejected (2026-08-25). Three places already exist: what each file is → section 8; the machine-readable list, hashes, commit SHA and skins → manifest.json; what to return after development → expected-back.md.

  • ⛔ A README becomes a third copy that drifts from section 8.
  • ⛔ Its content is identical in every DR — static text copied N times, and when the layout changes all N already-sent copies become false, with no way to recall them.

manifest.json spec versions#

A reader of spec 2 treats the missing field as an empty list.

Zero screens is normal#

⚠ Backend-only and simple-change FRDs have no worktree and no commit. The package must stand without screens/, and any validation demanding "at least one screen" would make those FRDs permanently unsendable.

Where the material comes from#

⭐ The worktree is the material. commitChanges runs at completion and the worktree is not removed (worktree remove exists only in reset and rollback), so as-is (before the commit) and to-be (after it) come from the same place.

⛔ Never add code that removes a worktree before delivery finishes — the material for the contract would be gone.

Pre-send checks — DevRequestPrecheck#

⭐ Two layers is the point. Merged into one, it becomes either all-blocking (ambiguous cases can never ship) or all-warning (things development cannot use ship inside the contract).

⛔ Builder does not write its own checker. Spec judgement is done by the checker shipped inside the planning repository (CheckerCommand). This class only translates that result into blocking or warning.

⭐ The checker runs only when send is pressed (instruction, 2026-08-25). The detail screen uses check(), which reports only what the DB already knows; checkForDelivery() is the only caller that runs the checker. Running it on every open made the same screen look different each time the result expired.

Sending#

The transmission target is registered per project in group management — Developer 연결 or GitLab 이슈로 전송. A project with neither registered shows 설정 필요, which is the normal starting state; the fields, validation and history semantics are in project setup.

The flow#

기획자 presses 개발요청 보내기
        │
        ▼
  CHECKING    전송 내용 확인      run the pre-send check NOW
        │                        blocked → nothing is sent, 전송 전 확인 says why
        ▼
  PACKING     전달 자료 준비      build the package, zip it, write manifest.json
        │
        ▼
  UPLOADING   개발팀에 전송       ONE call to the bound channel
        │
        ▼
  CONFIRMING  접수 결과 확인      map the answer onto a state
        │
        ├── proof of receipt ─────────────▶ 전송완료
        ├── cannot tell ──────────────────▶ 전송중   (re-send uses the SAME material)
        └── proof it never arrived ───────▶ 대기     (re-send starts over)

Those four names are the stages the detail screen draws, from DeliveryProgress.stages(). GET /{requestId}/delivery-progress returns the fragment the screen polls.

  1. 개발요청 보내기 runs the pre-send check at that moment. Opening the detail does not re-run it.
  2. If anything blocks, nothing is sent and 전송 전 확인 shows why. Fix it in the FRD work or the project settings.
  3. The send dialog takes notes for the development team, the expected completion date, the deployment date, a preceding development request and attachments. A preceding DR is never auto-selected merely because screens overlap.
  4. Builder prepares the package and sends it to the target registered on the project.
  5. A clear result becomes 전송완료; an unconfirmable one stays 전송중. An unclear state is never quietly reset to 대기.

Which channel a request goes to, and when that is decided#

DeveloperGateway is @Primary and routes; DevIssueGateway is the GitLab implementation it falls back to.

send(package, deliveryKey):
    bound = targets.bound(requestId)         already tied to a Developer target?
    if bound != null                     ──▶ send there, whatever the setting says now
    current = targets.current(projectId)     is Developer the project's current channel?
    if current == null                   ──▶ DevIssueGateway  (GitLab issue)
    targets.bind(requestId, current.id())    tie this request to that target — permanently
                                         ──▶ send to Developer

⭐ The channel is chosen once, at first send, and then frozen onto the request. Changing the project setting afterwards never moves work already in flight, which is what makes status polling, withdrawal and result collection keep working against the address the package actually went to. This is the reason adk_builder_developer_target keeps retired rows instead of overwriting.

The delivery key, and what "send again" means#

Every development request has one delivery key, and re-sending reuses it. That is what lets the receiving side recognise a second attempt as the same request rather than a new one, and it is why 전송중 can be resolved by asking "do you have this key?" (lookup) instead of sending blindly.

⚠ 전송중 re-sends the original material, unchanged. DeliveryJournal freezes the input and the fingerprint on the first attempt; a retry from 전송중 reuses them. Only a request back at 대기 rebuilds from scratch. Re-sending after an edit would otherwise deliver something different under a key the far side has already seen.

Reading the answer — DeliveryOutcome#

⭐ One rule decides everything: only proof that the other side never processed it means 대기. If we cannot tell, it is 전송중.

Answer State Why
200 / 201 with the delivery key echoedSENTReceipt is proven
200 / 201 without the echoSENDINGSee below
202SENDING"Accepted" is not "processed"
400 401 403 404 413 415 422NOT_SENTThe request itself was refused — the body never reached processing
408 429SENDING"Not now, later" — says nothing about whether it was handled
3xx, 5xx, any other 2xxSENDINGA moved address or a gateway giving up is not proof of non-processing
DNS failure, connection refused, TLS failureNOT_SENTbeforeBody() — provably never arrived
Timeout, disconnect before responseSENDING⛔ not beforeBody() — it may already have been received

⛔ Do not "fix" the echo check. A 200 without the delivery key echoed back stays 전송중, and that looks like a bug until you know why: corporate proxies and login pages also return 200. Without our own key reflected in the body there is no evidence the package reached the far side at all. Deleting the echoed test would convert every proxy interception into a false 전송완료.

⚠ 409 is deliberately unresolved. It can mean "already have this one" — effectively sent — or an ordinary conflict, which is a failure. docs/requests-to-dev.md asked development on 2026-08-10 and no answer has come back, so the code routes it with the general SENDING fallback and says to fix the table once the meaning is agreed. Do not close this in documentation ahead of that answer.

Two preconditions for any of the above being true#

These are not configuration preferences. The state mapping is only correct if both hold, and HTTP clients default the other way, so each must be actively switched off in the implementation.

  1. ⛔ No silent retry. Clients and corporate proxies commonly re-fire on a dropped connection or a 502. If that happens, nobody knows whether the package went once or twice.
  2. ⛔ No automatic redirect following. A 302 on a POST makes many clients re-issue it as a GET, discarding the body, and then receive a final 2xx. Builder would confirm 전송완료 having sent nothing. That is worse than sending twice, because a double send is at least visible.

Withdrawal#

WITHDRAWN is a state of its own, not a return to 대기.

⭐ It works only while the issue still carries the intake label — a label Builder sets, meaning development has not picked the work up. If development has started, their workflow has changed the label and the gateway refuses; we cannot undo someone else's work in progress.

⛔ Never map a withdrawal back to NOT_SENT. The issue is still alive, so a request sitting at 대기 would be sent again and open a second issue. The delivery key is kept, and the receiving side treats a fresh submission under the same key after a withdrawal as a separate attempt.

Delivery states#

State Meaning Available actions
대기Not yet sentSendable once the pre-send check passes. An FRD-sourced request can be deleted to return to FRD work
전송중Receipt unconfirmed, or the result needs checking개발요청 다시 보내기 after a duplicate-issue check
전송완료Receipt confirmedTrack development status. Withdrawal is possible while development is still at intake
취소The planner withdrew itRevise and send again

If a receipt lookup returns 404, the attempt is rolled back to 대기 with "개발팀에 접수 기록이 없어 대기로 되돌렸습니다" — the one failure that has no stored reason of its own, so DeliveryProgress.failureMessage supplies it rather than telling the reader to check a reason that is not there.

Why delivery is serial#

deliveryExecutor is core 1, max 1 with builder.delivery.queue-capacity (20). One send at a time, and a full queue is rejected back to the caller rather than silently dropped.

⚠ The queue holds storage paths, not file bytes. That is what makes a depth of 20 affordable — twenty queued sends cost twenty paths, not twenty ZIPs in memory. Reading the pool size alone does not explain the capacity; the two settings only make sense together.

Guard rails: max-archive-bytes (512 MB), minimum-free-disk-bytes (256 MB), plus asset-cache metadata size and TTL. Delivery deliberately does not occupy the AI or clone executors.

Supporting classes: DevRequestPackageBuilder, DevRequestPackageZipper, DevRequestManifest, DevRequestExpectedBack, DeliveryPrewarmer, DeliveryJournal, DeliveryRecovery, DeliveryAssetCache, DevIssueGateway, DeveloperGateway, DevHandoffGateway.

Development status#

Delivery state and development state are separate values. DevelopmentStatusSynchronizer polls GitLab issue labels every minute (builder.dev-request-status.fixed-delay-ms: 60000) and only ever moves the state forward.

Development state Meaning User action
대기Not sent, or status not yet determinedCheck the delivery state and sync errors
개발 접수Development received itCancellation can be attempted only here. If development already took it, the cancellation is refused
개발 진행 중In progressFollow the DR and the GitLab issue
개발 완료Completion confirmed from the labelPress 개발 결과 반영

개발 완료 does not mean automatic merge. The user must explicitly press 개발 결과 반영; the button does not appear if the result was already applied or the state is not complete. See Development result.
