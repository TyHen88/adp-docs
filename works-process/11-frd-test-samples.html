Trying it out

FRD test samples

Five requirement bodies to paste into step 1 of the wizard, chosen so that between them they walk every branch of FRD work: an existing-screen change, a new screen, a back-office screen, a screen-less change, and a one-line edit for resume and re-complete. They were run end to end on 2026-09-13 — 27 of 30 scenarios — so the “what actually happened” column below is measurement, not expectation.

The bodies are Korean on purpose

The planning repository, the screen documents and the interview are all Korean, and every run carries a system rule telling the model to write for a Korean-speaking planner. An English requirement will be analysed, but the screens it is matched against are named in Korean, so the samples stay in the language the product runs in. The explanation around them is English.

Before you start

Preconditions

  • A project in READY — its clone must have landed
  • The signed-in account has Claude connected
  • A planning repo with real screens in the area you write about

Two safety rules

  • Do not send the development request. Completion stops at the FRD branch commit and the package — nothing reaches the remote
  • Start every test title with [e2e] so test FRDs never mix with real ones

What it costs in time

Measured on a clone of 4,511 files / ~181 MB: the wizard takes 2–12 minutes depending on how many questions the interview asks, an AI screen draft 54–130 seconds, and one completion 217–294 seconds.

If your project is different

These five sit in one area of one planning repo — 가맹점 방문 예약 in a regional-currency project — deliberately, so the AI has neighbouring screens to find. For another repo, keep the shape and swap the domain: see writing your own.

The five samples

R1 — an existing screen changes

Title: [e2e] 익산 웹뷰 방문 예약 취소

이용자가 「나의 방문 예약」에서 확정된 방문 예약을 직접 취소할 수 있어야 한다. - 취소는 방문 예정 시각 1시간 전까지만 가능하고, 그 뒤에는 취소 버튼을 보여 주지 않는다. - 취소할 때 취소 사유를 목록에서 하나 고르고, 「기타」를 고르면 사유를 직접 적는다. - 취소가 끝나면 예약 목록으로 돌아가 상태가 「취소됨」으로 바뀐 것이 보여야 한다. - 이미 방문이 끝났거나 가맹점이 취소한 예약은 이용자가 취소할 수 없다.

Meant to prove: the baseline path — one or two existing screens change, nothing new. What actually happened: the repository had no 「나의 방문 예약」 screen, so the interview corrected the scope to two new screens plus one existing (the 전체메뉴 modal) after 4 turns, about 5 minutes. That correction is the interview working.

R2 — a new screen appears

Title: [e2e] 익산 웹뷰 가맹점 즐겨찾기

이용자가 자주 가는 가맹점을 즐겨찾기로 등록해 두고 모아 볼 수 있어야 한다. - 가맹점 상세 화면에서 즐겨찾기 등록·해제를 한 번의 동작으로 바꾼다. - 「즐겨찾는 가맹점」 목록 화면을 새로 만들어 등록한 가맹점을 최근 등록순으로 보여 준다. - 목록에서 가맹점을 누르면 기존 가맹점 상세로 이동한다. - 전체메뉴에 「즐겨찾는 가맹점」 진입 항목을 더한다. - 로그인하지 않은 이용자가 즐겨찾기를 누르면 로그인 안내를 보여 준다.

Meant to prove: two existing screens plus one new list — the mixed case, and the one to use for the AI draft and the screen chat. What actually happened: 5 interview turns over about 12 minutes; answering one question by hand and then correcting the summary made the AI point out a contradiction in the correction and ask two more questions.

R3 — the other system and the other facet

Title: [e2e] 제주 백오피스 방문 예약 현황 조회 · register it with facet 제주 and system 백오피스

운영 담당자가 가맹점별 방문 예약 현황을 기간으로 조회하고 엑셀로 내려받을 수 있어야 한다. - 조회 조건은 기간(시작일·종료일)과 가맹점이고, 기간은 최대 3개월로 제한한다. - 목록에는 예약일시·가맹점·이용자·인원·상태를 보여 주고, 상태로 한 번 더 걸러 볼 수 있다. - 행을 누르면 예약 상세를 옆에서 보여 준다. - 조회 결과를 엑셀로 내려받을 수 있고, 내려받기는 조회 조건을 그대로 따른다.

Meant to prove: the facet axis and the skin — the workbench preview should come up in the back-office skin, and the candidates should be back-office screens. What actually happened: 2 turns, about 4 minutes, two new screens and six backend items; the AI said plainly that the repository has no visit-reservation screens rather than inventing a match.

R4 — no screen at all

Title: [e2e] 방문 예약 알림 문구 정책

방문 예약 알림 문구를 표준용어에 맞춰 정리해야 한다. 화면 변경은 없다. - 예약 확정·예약 취소·방문 1시간 전 세 가지 알림의 문구를 정한다. - 문구에는 가맹점명과 방문 일시를 넣고, 표준용어에 없는 말은 쓰지 않는다. - 이용자가 알림 수신을 꺼 두었으면 보내지 않는다. - 발송에 실패하면 다시 보내지 않고 기록만 남긴다.

Meant to prove: the backend-only branch — zero screens, and the 개발요청서 바로 만들기 exit. What actually happened: the AI settled on 0 screens and 5 backend items, but left 4 items under 확인 필요, and the fast-track button only appears when none are open — so it did not show. Pressing FRD 작업하기 instead saw zero screens and completed straight into a development request.

R5 — one line, for resume and re-complete

Title: [e2e] 익산 웹뷰 방문 예약 상세 안내문

방문 예약 상세 화면 아래쪽에 방문 유의사항 안내문을 더해야 한다. - 안내문은 예약 상태가 「확정」일 때만 보여 준다. - 내용은 신분증 지참 · 방문 시간 준수 · 취소 기한 세 줄이다. - 기존 버튼과 겹치지 않도록 버튼 위에 둔다.

Meant to prove: the smallest possible FRD, so it can be completed, resumed from the development request, and completed again without waiting for a long interview. What actually happened: 2 turns, about 2 minutes, one existing screen.

A run that covers the important paths

Creating an FRD is the slow part, so make five and layer the scenarios on top of them. The first four lines below cover every high-priority path in about 90 minutes.

1
R1 — the baseline
wizard → 작업하기 → 직접 수정 one label → 완료
Gives you the reference timing table for every later completion.
2
R2 — the AI paths
answer one question by hand → 다시 인터뷰하기 → AI draft → screen chat
Try 완료 while a draft is still running: it must be refused, with no run created.
3
R5 — the completion gate
drop files into the worktree, complete, read the refusal, remove, repeat
A conflict marker and a NUL byte must be refused; broken HTML and an oversized HTML must pass with a diagnostic. Then resume from the DR and complete again.
4
Two FRDs at once
press 작업하기 in two tabs within 3 seconds · complete one while editing the other
Both must reach DRAFTING with one worktree each; the second may wait on the project lock but must not fail.
5
R4 and R3 — the edges
zero screens · the other facet and system · markers, memos, state cases
Widening, not proving: run these when the four above are green.

Already known — do not re-report these

Rough edges the 2026-09-13 run found, filed as issues

A completion refusal shows only “결과 검증 단계에서 중단”; the file and the code are in the log alone. The post-edit 375px check does not compare against a baseline, so a pre-existing overflow can block a new edit. Starting the same FRD twice drops the second request on an empty /pick screen. A zero-screen FRD still creates a worktree and branch. Re-completing rewrites most of the preserved material rather than reusing it. And the planning repo's node checker exceeds the two-minute cap on a very large document.

Writing your own

A body the interview can work with names four things: who acts, why, from what starting condition, and what the outcome should be. Add the conditions that change the answer — permissions, error cases, limits, retention — because those are exactly what the AI would otherwise have to ask about, and every avoided question saves a turn.

Pick an area with neighbours

All five samples sit in one neighbourhood on purpose: the AI finds screen candidates by reading the repository, so a requirement in an area with several existing screens produces a realistic mix of existing and new. A requirement about something the repo has never heard of produces all-new screens, which is a thinner test — and, as R1 shows, the interview will tell you so.
