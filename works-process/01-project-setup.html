Process 1

Project setup and the GitLab repo

Only the super account reaches this screen, at /admin/projects. What it creates is deliberately flat: one project = one planning repo = one server clone. There are no groups and no account-to-project mapping — every logged-in planner sees every registered project, so the only thing that gates a project is whether its clone has landed.

What you register

FIELD 01
Name
Unique and non-blank. Re-checked on the server: the form's required lets a name of spaces through.
FIELD 02
Repo URL
The planning team's GitLab repo. They own it; the builder only ever holds a clone.
FIELD 03
Default branch
Cloned with --branch, and every later fetch and merge tracks it.
FIELD 04
Access token
Scoped to this one repo, sealed before storage. It does all four jobs: probe, clone, fetch, push.
Two more values are fixed in the same submit

The platform code (2–4 upper-case characters or digits) and the application facets. The platform code can never be corrected afterwards: standard screen-ID numbering starts as soon as the clone lands, and an assigned ID is never rewritten.

The path

01
Admin submits the form
POST /admin/projects · name · repoUrl · defaultBranch · platformCode · token
Guarded by @PreAuthorize("hasRole('SUPER')") on the whole controller
↓
02
Verify the repo, before anything is saved
git ls-remote --heads <authenticated url> <branch> · 20s timeout
Fails → the registration is not saved at all. Empty output means the branch is wrong, not the token.
↓
03
Seal the token, draw the ID, insert the row
SecretSealer.seal(token) → IdSequence.next(PROJECT) → adk_builder_project
Numbering runs after the probe: in front of it, every rejected attempt would burn a sequence number for good.
↓
04
Clone in the background
git clone --branch <branch> <url> <data-root>/projects/<id>/clone · 30 min cap
The browser was redirected at step 03. Nobody watches a progress bar.
RECEIVING cloning, invisible to planners → READY or FAILED with a reason and a Retry button

The moment the clone lands

01
State becomes READY, in its own short transaction
ProjectService.cloneSucceeded(projectId)
The project appears in every planner's list, and a notification is published.
↓
02
Systems are read out of the clone
manifest.json → systems[] → adk_builder_project_system
The manifest is the only source for which systems exist; display names are added later by the admin. A missing file yields an empty list, never an exception.
↓
03
Standard screen IDs are numbered
screenIds.assignQuietly(projectId, accountId) · its own thread
Uses the platform code fixed at registration — which is why that field cannot be edited afterwards.
Steps 02 and 03 are allowed to fail quietly — and the submission itself is wrapped

The clone already succeeded, so nothing here may flip it back to FAILED. Even submitting the async numbering is wrapped in its own try: a rejected task throws TaskRejectedException synchronously on the calling thread, where the worker's outer catch would have called cloneFailed and turned a finished clone into a failed one. Repository update is the retry for both.

Keeping the clone fresh

There is no scheduled refresh. An admin presses Repository update, and five steps run in order — all of them, or none.

1
The clone must be clean
git status --porcelain
Any local change stops the update here.
2
Bring down what the planning team pushed
git fetch <url> <default branch>
Uses the same project token as the clone.
3
Advance the local branch
git merge --ff-only FETCH_HEAD
Fast-forward only, so no merge commit is ever invented in the clone.
4
Re-read the systems
manifest.json → systems[]
A newly added system appears here, not at the next restart.
5
Number anything that arrived unnumbered
screen-ID assignment
Same swallow rule as the clone: a failure here does not undo the update.

When it goes wrong

Clone failed

FAILED, with the reason trimmed short enough to read on screen. Retry deletes the half-written directory first — a clone killed at the 30-minute cap leaves one behind, and without that cleanup every later attempt dies on “destination path already exists”.

Token expired

Retry cures a dropped network, never an expired credential — it would fail in the same place forever while the project stands frozen. There is a separate field for the token alone, re-probed on submit; name, URL and branch are untouched.

Start over

Reset clears the project's data and clones again, guarded only by typing the confirmation. It is the last resort, not the first, because it discards everything built on that clone.

Why the failure can be written down at all

CloneWorker.clone carries no @Transactional, and the class comment says why at length. With one, an exception thrown inside — unsealing the token, say — would mark the shared transaction rollback-only, so the catch that records the failure would itself fail with UnexpectedRollbackException and the project would freeze in RECEIVING. It would also hold a database connection for thirty minutes. The work is split into three short stretches instead: read, file work, write the result.
