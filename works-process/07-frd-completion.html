Process 5

FRD completion — closing the work

Completion is not a development quality gate. It is the safe saving and handing over of planning content. Everything below follows from that one sentence — including the things it refuses to block on.

Blocks completion

  • A save, read or recovery failure
  • An unsafe real file path
  • An unresolved merge conflict

Does not block completion

  • Missing screen links or references
  • HTML structure problems
  • Design issues and review counts
  • External quality-check failures

Non-blocking findings are not discarded: they are pinned into the development request's 확인 사항. Thresholds are never raised automatically, and tool-operations noise stays in the server log.

2 MB input cap · no tools · strict JSON parsing → FrdCompletionMergeValidator
An empty result, generic prose or comments-only output is rejected as a candidate. Git problems are never handed to the planner.
↓
06
Wait-phase checks only, then publish success
path · readability · size · binary contamination · unresolved conflict markers
The delivery-baseline commit is made here — the commit the development request is later built from.
↓
07
Prepare DR material, and review in the background
feature definitions · test scenarios · HTML/JSON quality · external links
Both run after success is published, on the existing async worker.
What the speed pass moved out of the wait — and what that costs

Quality analysis and link checking left the waiting path. In exchange, the development request records a “priority check result not yet confirmed” notice; when the result lands, only that notice is replaced — existing confirmation items and test scenarios are preserved. A document already being delivered, or deleted, is not touched. On a restart or a failed check the notice simply stays, and completion is never rolled back. WAIT_TOTAL and BACKGROUND_REVIEW are logged separately so the two times are measured apart.

“The MD exists” and “the MD is ready” are different judgements

A document holding only marker descriptions or empty scaffolding is not ready. An existing history's HTML and MD are reused only when they match the merged HTML; otherwise generation is requested again. A human-written ready document is never overwritten, and a generation failure does not cancel completion.

What completion does not do

It does not merge to-be into the default branch

core/<system>/pages/ holds as-is. If completion merged the planner's drawing there, the next FRD would read it as the current state of the system. Fact reaches that folder only through the development result.

It does not delete the branch

The worktree survives REVIEW and is not removed just because the FRD is marked DONE — only after the commit and push succeed, and only with nothing uncommitted. The branch is kept regardless: it is the only evidence of what changed and why. Old phrasing like “closing = push, remove the worktree, release the lock” survives in places; do not add branch deletion to it.

So FRD 작업 완료 closes the work and keeps the branch, and stops there. On failure the work is preserved and the cause reported; the run supports retry and cancel, and a restart-abandoned run is swept up at boot.
