Process 9

On the dev side — what happens when it lands

This is the far side of one HTTP call. Builder does not own that codebase, so everything on this page is one of two things: what Builder sends and will accept back, which is ours, or measured behaviour of DEVELOPER, which is theirs and dated. Where the two disagree, the code on our side and the returned archive are what decide.

The intake call, from their side of the wire

01
A multipart POST arrives with eleven fields and a ZIP
POST {base}/intake · no auth header · groupId is the connection identity
There is no token, so an unknown group is the one thing that can reject the caller outright.
↓
02
They validate before accepting
title ≤ 500 · body required · ZIP must begin with PK · file ≤ 20 MB, request ≤ 25 MB
400 input error · 404 unknown group · 409 the delivery key belongs to another group · 413 too large — each as {"message":"…"}.
↓
03
A new work request is created, or the existing one is returned
201 new · 200 an active request with that delivery key already exists
Both answer {"deliveryKey":"DRK-0000005"} — the echo Builder needs before it will call the send complete.
↓
04
Their admin account gets a notification
「[DR-005] {title} 접수」 → /requests/{id}
Only on 201. A resend answers 200 and raises nothing, so nobody is pinged twice for the same work.
FieldWhat they check
titleRequired, 500 characters or fewer — and it carries no DR number, because the number travels separately
bodyRequired. Structured JSON, UTF-8
fileRequired. First two bytes PK; 20 MB per file, 25 MB per request
requestNumber · workNumberRequired, 20 characters or fewer — DR-005, and FRD-002 or SRT-003
workTypeRequired: FRD or SRT
deliveryKeyRequired, matching DRK-[0-9]{7}
groupIdRequired. An unknown group is a 404
the two dates · plannerNameOptional; empty strings allowed. The name feeds their inbox's planner column and filter

What they actually look at

The inbox row

The work request appears in their 작업 수신함, identified by delivery key rather than DR number — DR numbers restart at 1 in every project, so they are not unique over there. The planner's name is a column and a filter, which is why Builder sends it even though a development request has no owner column of its own.

The detail view — from the JSON, not the markdown

body is the same material our detail screen draws, laid out in the same sections: basic info, the original request, scope, per-screen changes, out-of-screen implementation, items to confirm, acceptance criteria, the file tree, and what must come back. It is JSON so they render the same view instead of re-interpreting prose.

The ZIP, for everything visual

dev-request.md is the same content as prose; manifest.json lists every file with size and sha256; screens/<system>/<screenId>/ holds as-is and to-be as HTML and MD side by side, plus changes.md. The asset folder is copied whole, so opening a to-be file renders with styles and no rewriting.

Why as-is travels too

The contract is “from this, to that”. Sending only to-be would make them diff it themselves and leave nothing to settle a later argument about what the screen used to do.

What they must send back

Section 11 of dev-request.md states it plainly: fill in expected-back.md with the actual implementation result, keep to the shapes manifest.json declares, and report anything that was not in the plan as a separate review item there. The tree it prints is the reply's shape:

DR-007/ ├─ manifest.json the machine contract — mirrors what was sent ├─ expected-back.md the same file, filled in with what was really done ├─ artifacts/ │ ├─ unit-test.md when the request had out-of-screen items │ └─ integration-test.md when the request had acceptance criteria └─ changes/ ├─ summary.json what changed └─ files/<repo>/<original path in that repo>
Only four things are allowed in the reply archive

manifest.json, expected-back.md, changes/** and artifacts/**. Anything else is rejected on arrival. The screen axis and the domain axis were removed from the return contract in September 2026: what development returns is “what changed” and “the verdict on the acceptance criteria”, and the artifacts for the planning repository are built by the side that knows that repository.

The published API contract still shows the removed keys

docs/developer-api-contract.md's body example still lists expectedBack.screens[], domains[] and domainPayload. Those are dead text from before the replacement — the code emits backendChanges[] and testArtifacts[] only, and the class carrying them says in as many words that leaving the old wording around had already made both repositories read the old contract as current. Trust the code and the validator.

Tests come back as documents, never as code

Builder does not know the operational source system, so it cannot read development's code. Both test kinds arrive as markdown at fixed paths, and Builder writes the questions first — TC number, condition, action, expected result go out inside expected-back.md. Development fills in only the actual result, the verdict and the evidence, which is what lets the screens count returned results per test case.

RuleWhat the validator requires
Contract matchThe manifest's test-return contract must equal the one that was sent — kinds present, no duplicates, same paths and counts
Required filesA required artifact must exist and must not be empty
Target headings### N. <target>
Test-case headings#### TC-NNN … — three digits
VerdictsExactly one of 성공 · 실패 · 미수행
PlaceholdersA field still holding <something>, or left blank, is rejected — an unfilled template is not a result

This applies to specVersion 3 packages. A spec-3 result with no return contract to compare against is refused outright, and spec-2 packages had no test contract at all, so they are read as an empty list rather than as a failure.

How Builder learns any of this happened

They never call us

There is no inbound API into Builder. Builder polls status and results itself, every 60 seconds by default, keyed by delivery key — and each request keeps polling the connection version it was actually sent with.

Their statusMeaning on their sideWhat Builder records
INTAKEReceived개발 접수
WAITING · DEVELOPING · DEVELOPED · REVIEWINGQueued, in development, developed, in review개발 진행 중 — all four fold to one
COMPLETEDReview passed, and their 완료 처리 uploaded the result ZIP개발 완료
REJECTEDSent back, with a reason of 1–4,000 characters개발 반려, reason shown on the detail screen
WITHDRAWNBuilder withdrew itNothing — the state is left alone and the poll is recorded as failed

An unknown code changes nothing and is logged as a failed cycle. A status that moves backwards, or changes after completion or rejection, is refused the same way: the existing state is kept and an error recorded. As measured, only INTAKE and WITHDRAWN are emitted today — the other six are names both sides agreed on for when their transitions are implemented.

Picking up the result

01
Ask for the list
GET {base}/intake/{deliveryKey}/results → [{id, body, zip}], newest first, [] when none
Builder reads id and zip only; body is for people. An item missing either is skipped.
↓
02
Only the newest batch is applied
id is monotonic · a re-delivery is a NEW item
Changing the contents under an existing id means Builder treats it as already applied and skips it. Same batch with a different ZIP is recorded as an error.
↓
03
Download, then validate before extracting
≤ 2,000 entries · ≤ 10 MB per file · ≤ 100 MB total · attachment host must be the registered one
The manifest's devRequestId accepts the label or the internal id — development sees DR-007, so demanding the id would reject correct replies.

Two things the other side cannot do for us

They cannot un-send a withdrawal

Withdrawal is accepted only while the request is still at INTAKE, checked atomically on their side: 200 with status: WITHDRAWN, 404 for an unknown key or a mismatched number, 409 once development has moved past intake. Builder treats anything other than 200 as “not confirmed” and keeps the request where it was.

They cannot approve a merge

COMPLETED says the work is finished over there. It says nothing about whether the planning repository should change — a planner must press 개발 결과 반영 for that. See Development result.
