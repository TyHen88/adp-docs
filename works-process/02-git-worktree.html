Process 2

Git and worktrees

Every path on this page is computed in one class, ProjectPaths, under builder.data-root. That matters more than it looks: after a restart the server has to recompute the same folder from the same ID and find the existing worktree again.

What sits on disk

<data-root>/projects/<projectId>/ ├─ clone/ the server clone — nobody works in here ├─ worktrees/frd-0000025/ one FRD, one branch, one person │ srt-0000004/ an SRT fast track │ dev-request-merge-… cut for a merge, then removed ├─ received/ uploaded originals └─ dev-request-packages/<id>/ what goes out to the dev team
Two of those folders are outside the clone on purpose

received/ and dev-request-packages/ sit beside the clone, never inside it. Anything inside the clone is something git can see, stage and push — and neither an uploaded original nor an outbound copy belongs in the planning team's repo.

Cutting a worktree for one FRD

Analysis and the AI interview only read the repo, so they need no worktree. The first write is the planner pressing FRD 작업하기, and that is where one is created.

01
The FRD must be in SCOPE_REVIEW
state check · owner check
A worktree is the moment work becomes writable, so the state gate comes first.
↓
02
The clone and its default branch must be healthy
clone/.git present · branch resolvable
Fails → the FRD stays in SCOPE_REVIEW and the screen says what to do.
↓
03
Create, or reuse what is already there
git worktree add -b frd/<id> <folder> HEAD — or worktree add <folder> <branch>
Same branch and same folder already paired → reused, never recreated. Branch present without a folder → the folder is reattached to it.
↓
04
Only now does the state change
FRD state → DRAFTING
Git work and a database write cannot be one transaction, so the order is the safety.
ItemRule
Branchfrd/{FRD DB ID} — e.g. frd/0000025
Folder<worktreeRoot>/frd-{FRD DB ID}
BaseThe clone's HEAD at the moment the button is pressed
OwnerThe FRD's owner_account_id — one worktree, one person
Named by DB ID, never by the display number

FRD-025 is for people and can change; 0000025 is the recovery key. If the folder exists but git does not know it, or it points at a different branch, nothing is overwritten or deleted — the screen reports that recovery is needed. And if the state flip fails after a fresh worktree was made, only that one is cleaned up: an older one may hold the planner's work.

Closing the work

The worktree goes, the branch stays

A worktree survives REVIEW, and marking something done does not remove it. It is removed only after the commits are safely in the planning repo, and only when nothing is uncommitted. The branch is kept: it is the only record of what changed and why.

to-be never merges into pages/

core/<system>/pages/ on the default branch holds as-is — what the running system actually looks like. Facts arrive there through the development result. Merging a planner's drawing in would make the next FRD read it as reality. Writing that file inside a worktree branch is fine and expected.

Getting commits out

IDENTITY
Shared account pushes
One builder account holds the credential; planners never need a GitLab account or a personal token.
ATTRIBUTION
The planner is the author
In git the author and the pusher are different things, and an author needs only a name and an email.
NOT USED
No merge request
Nobody reviews the planning repo. An unmerged MR keeps work off the default branch and off other planners' screens, and the cleanup that removes worktrees never runs.
One push at a time, enforced by a single worker

A short database lock cannot do it: once released, another request grabs it while git is still running. Holding a transaction across the whole git run would drain the connection pool, and a rollback would erase the record of commits that already went out. With one server, one worker is the cheapest correct answer — so there is no “how many times do we retry a rejected push” question: nobody is ahead of you in the queue.

If content collides, the later person redoes the whole thing

Queueing prevents two pushes at once, not two people editing the same file. One conflicting file out of three means the whole work item is redone — leaving the conflicted part for the planner produces a screen they cannot resolve, and showing them git is where they stop. Collisions come from two directions: inside the builder (requirements, definitions, the IA of one system) and from a planning-team member editing directly in GitLab, which can touch any file.

The only four places that push

ClassWhat it pushes
IaPublisherThe confirmed menu tree (IA) snapshot
DevRequestBranchMergerThe merge of a completed FRD into the default branch, and the branch cleanup that follows
DevResultApplyWorkerThe development result applied back into the planning repo

Three classes, four call sites. Everything else in the codebase commits into a worktree and stops there.
