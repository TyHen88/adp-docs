Process 4

FRD workbench — the drafting loop

One worktree, one person, one screen at a time. An FRD with no screens selected works on out-of-screen implementation requirements and document scope instead — the loop is the same, minus the preview.

The loop

01
Pick a screen in the left list
artifacts/frd.html · one FRD, many screens
Screen states are independent of the FRD's own state.
↓
02
Make the draft, then work on detail
ScreenMockupWorker · Edit(/<target>/<screen>.html) — one path, nothing else
Claude edits one HTML file directly inside the worktree; the resulting HTML is not returned in the response.
↓
03
Ask for the change you need, specifically
FrdScreenChatWorker · 4,000 characters per message · one AI edit at a time per FRD
Routing is decided by the last message, not the button — typing the sentence takes the same path as the menu item.
↓
04
Check the screen and the explanation together
preview · change list · markers
Only the screen that failed is FAILED; the others and the FRD are unaffected.
↓

Saving runs the spec checker automatically and reports back only when something fails.

The AI 제안 menu

ItemWhat comes back
디자인 시안 비교Two design proposals and an apply button
문구·용어 맞추기The corrected screen plus a before → after (basis) list

Only items that produce an outcome are listed

Pressing one must change the screen or give something to choose. An item that returns a review comment leaves the planner to turn that comment back into a request, and that was measured getting stuck: “review the design rules” → “you are following the rules” → “fix what you pointed out” → “I did not say anything was a violation.” Design rules are read on every edit anyway.

Wording alignment needs the policy and standard-terminology documents registered in 정책·표준용어. With none registered the AI is not run at all and the planner is told to register them. Words with the same meaning but different spelling are corrected; anything whose business meaning would change is left as 확인 필요.

Changing a screen without an AI run

Direct element edits

Text and a deliberately narrow set of properties on one selected element, saved as a new screen version. Spacing and font sizes come from a fixed list; color and background-color accept design tokens only, so a direct edit cannot break the design system.

Markers vs memos

A marker is an execution note pinned to an element — 기능, 정책, 예외, 권한, 확인 요청 — and it is fed into the AI conversation and into the development request. A memo is a comment for people. Marker text is worth writing carefully; memo text is not read by anything.

State cases

상태 추가 creates a sub-screen from the current one — 검색 결과 없음, 권한 없음, 저장 실패. A state screen cannot nest another, and none can be added to a screen the AI is working on.

History and comparison

Restoring a history entry restores the files and that point's marker snapshot. The comparison view lines up only the same screen and the same facet — and it does not restore anything: looking at a version is not applying it, which is what makes it safe to browse while work is in flight.

Writing into the worktree is expected

The draft worker writes pages/<screenId>.html inside the worktree branch, and the development-request package takes its material from exactly there. The prohibition is only on carrying that into the default branch, where pages/ must stay as-is.

Write admission — completion beats the planner

While completion holds the FRD, an interceptor on /projects/** refuses user writes with a message telling them to check the progress first. While an ordinary AI run is in flight it keeps a reservation, not a lock, so reads and other screens are untouched.
