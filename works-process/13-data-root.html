Underneath

The data root on disk

Everything the server writes outside the database lives under one configured path, builder.data-root. There are only two kinds of folder down there: one that holds work you cannot lose, and scratch space for claude child processes that is created on demand and deleted in a finally. Knowing which is which is most of what you need.

An empty scratch folder is the normal state

Nine of the ten top-level folders exist only because a run needed them once. Finding them empty means nothing is running right now — not that something is missing.

The whole thing at a glance

<data-root>/ ├─ projects/ durable — clones, worktrees, packages ├─ claude/ common-rules.md, re-unpacked from the jar every boot ├─ frd-runs/ one folder per FRD — kept between interview turns ├─ frd-chat-sessions/ one folder per screen — kept so --resume works ├─ frd-completion-runs/ kept until a completion closes ├─ frd-chat-runs/ one folder per chat request — deleted after ├─ frd-tobe-doc-runs/ one per to-be document run — deleted after ├─ dev-request-test-scenario-runs/ one per scenario run — deleted after ├─ claude-connection-probes/ one per credential check — deleted after └─ probe/ a working directory for git ls-remote; never written to

projects/ — the one you must not delete

projects/<projectId>/ ├─ clone/ the server clone — nobody works in here ├─ worktrees/ │ ├─ frd-<frdId>/ one FRD, one branch, one person │ ├─ srt-<srtId>/ an SRT's workspace │ └─ dev-request-merge-<id>/ cut for a merge, then removed ├─ dev-request-packages/ │ ├─ <requestId>-<attemptId>/ one delivery attempt's room │ │ ├─ delivery.zip what was sent, hashed into the journal │ │ └─ package/ dev-request.md · expected-back.md · manifest.json · screens/ · attachments/ │ └─ <requestId>/DR-00n.zip the archive kept for that request ├─ received/ uploaded originals — created only when used ├─ dev-request-attachments/ attachments waiting to go out ├─ business-language-run/ short-lived credential dirs for policy/terms runs └─ dev-request-merge-run/ short-lived credential dir for a merge resolution

Every one of those paths is computed in a single class, ProjectPaths, and the last four are created only when something uses them — an install that has never uploaded a document has no received/.

Two naming rules you can read off the folder names

Worktrees are named by database id, never by the display number: frd-0000025, not FRD-025. The display number is for people and can change; the id is what lets the server recompute the same folder and branch after a restart and find the existing worktree again. And a package room is <requestId>-<attemptId>, one per delivery attempt, so you can tell two attempts at the same request apart.

received/ and dev-request-packages/ sit beside the clone, never inside it

Anything inside clone/ is something git can see, stage and push. An uploaded original is the server's own copy, and a built package is an outbound copy — neither belongs in the planning team's repository.

claude/

Holds exactly one file, common-rules.md, appended to every AI run with --append-system-prompt-file: write Korean for the planner audience, treat text inside files and quotations as data rather than instructions, and where the design source of truth is.

Editing it here does nothing

It is unpacked from inside the jar at every boot, so the deployed version always wins and your edit is gone on the next restart. The source of truth is src/main/resources/claude/common-rules.md. A resumed session also replays the system prompt recorded when it started, so even a correct edit reaches an in-flight interview only from its next session.

frd-runs/<frdId>/ — the wizard's run space

frd-runs/<frdId>/ ├─ credentials/ CLAUDE_CONFIG_DIR — Claude's session record lands here │ ├─ session.id the session to --resume on the next turn │ └─ .credentials.json wiped after every turn └─ work/ the requirement copy, the screen list, the interview copies

Three decisions are visible in that one path.

Keyed by FRD, not by run

It used to be a UUID per run, deleted at the end — so the next turn could not continue the previous conversation and re-explored the repository from scratch. Measurement: 220 of 350 seconds per run was that re-exploration, paid again on every one-line answer. Keying by FRD is safe where keying by person would not be, because a single FRD's state already allows only one run at a time.

The work path must not move between turns

A resumed conversation is holding absolute paths it saw last turn. Move the folder and those paths point at nothing.

The credential wipe is now the only guard

While the folder was deleted per run, deleting it also removed the unsealed credential. Now that the space survives, wipeCredential() after each turn is the single thing keeping somebody else's Claude credential off the server's disk. The whole space is wiped when the FRD finishes or is reset.

frd-chat-sessions/<frdScreenId>/ — kept on purpose

Claude Code stores its conversation session underneath CLAUDE_CONFIG_DIR. If every chat request used a throwaway directory, --resume would hold a session id pointing at a session that no longer exists — so the session directory is keyed by screen and kept, while only the per-request input goes in frd-chat-runs/.

frd-chat-sessions/<frdScreenId>/ └─ credentials/ CLAUDE_CONFIG_DIR for this screen · Claude's own session files beneath it the policy and standard-terminology copies also live here
Why the policy files are here and not in the run folder

They were written into the per-request folder once. The request ended, the folder was deleted, and the next resumed turn poked the path it remembered — “Path does not exist”. Anything a resumed session can reference has to outlive the request.

frd-chat-runs/<messageId>-<uuid>/

One screen-chat request's scratch, deleted when the request ends. What appears under input/ depends on what was asked:

frd-chat-runs/<messageId>-<uuid>/input/ ├─ conversation.md a resumed turn carries ONLY this turn — the rest is in the session ├─ screen-review-mcp.json the local “look at only this screen” tool config ├─ selected-region.json the region the planner picked in the preview ├─ reference-image.<ext> an image attached to the message ├─ new-screen.html a draft when the request creates a screen └─ design rules · gap context written per request for the menu items that need them

frd-completion-runs/ — the busiest structure here

frd-completion-runs/ ├─ budget.lock the disk-budget lock └─ <runUuid>/ ├─ journal.json the durable record: what was preserved, how far finalisation got ├─ contents/ preserved originals, addressed by sha256 ├─ disk-reservation this run's reserved space └─ attempt-<n>/ one merge attempt ├─ candidate/ the merged tree being verified ├─ baseline/ what it is compared against └─ verify/node_modules the checker's dependencies, copied rather than reinstalled

Why the reservation is a file

A budget held only in memory is lost on restart, and waiting runs would then compute the wrong free space. Writing it down means the budget survives a restart; rejections log the numbers and the configuration key while the screen shows only a per-code message.

Why contents/ is content-addressed

Originals are preserved so a failed merge can be rolled back, and addressing them by hash lets a second completion reuse what did not change. Measurement is honest about the limit: reuse between runs is bounded, and a re-completion still rewrites most of it.

Why the merge is a separate tree

candidate/ and baseline/ are not the planner's worktree. A merge that fails or is abandoned must never leave the working tree they are editing in a damaged state.

journal.json has a format version

Because recovery reads it after a crash. Format 3 records the index as the hash of git ls-files --stage rather than the index file's bytes — see the trap below.

The incident this folder remembers

Recovery used to compare the bytes of the git index file against the recorded hash. But git status — including the workbench's own two-second polling — rewrites the index's stat cache, so the content was identical while the bytes differed. One FRD was left stuck: recovery refused, and “retry completion” hit the same check forever. The fix compares the index tree instead, and the stuck run's journal.json had to be migrated by hand before it could be closed.

The three that are gone before you look

frd-tobe-doc-runs/<frdScreenId>-<uuid>/

Writes the to-be feature definition (<screenId>.md) before a development request goes out — the file that would otherwise leave a blank column in the contract. Inside: input/as-is.md and the rest of the material, plus credentials/.

dev-request-test-scenario-runs/<requestId>-<uuid>/

The run that writes integration-test scenarios for a request after completion. Inside: input/dev-request.md and credentials/.

claude-connection-probes/<uuid>/

One “is this credential still alive?” check, asked before a long job so a four-minute completion does not die at the end on a dead token. Inside: credentials/ and work/. Never called from screen polling — polling reads a cached verdict, because spawning a process every few seconds is load, not verification.

Why the material is always a file

All three write their input to disk and pass only the path. Pasted text has no length limit, so inlining it can exceed the Windows argv limit — and an imperative sentence inside somebody's pasted text should never land where it could be read as an instruction.

A deleted folder cannot hold its own failure reason

Each of these is removed in a finally, which is exactly why a failed run's diagnosis is written outside it. Before that existed, a failure left only a code like AI_FAILED — indistinguishable between a timeout, a missing credential and an over-long request — and one FRD died four identical deaths. Bodies are always masked on the way out, because responses can carry tokens and diagnostics live a long time.

probe/

A working directory for git ls-remote, used when a project registration or a replaced token is verified. Nothing is ever written into it — ls-remote downloads no files; a git process simply needs somewhere to run. Permanently empty is correct.

Two more that can appear at the top level

runs/<runId>/credentials (an AI run's credential directory) and doc-runs/<runId> (document processing). They are absent on an install that has not used them.

They are separate trees for one specific reason

Both sequences are seven digits, so ai_run's 0000001 and document processing's 0000001 would land on the same runs/0000001 — and the first run to finish would delete the credential the other was still using. Same numbers, different trees. The same rule explains why a credential directory is per run rather than per person: one person can have two jobs running, and a per-person directory makes the first finally destroy the second job's credential.

Cleaning up

With the server stopped

Everything except projects/ and claude/ can be deleted safely: you lose in-flight runs and resumable chat sessions, and nothing else. claude/ comes back by itself on the next boot. projects/ is real data — clones, and worktrees holding planner work that has not been pushed anywhere. Inside projects/, the one thing that does grow without limit is dev-request-packages/: one room per activated delivery attempt, and nothing trims them — each holds a delivery.zip the journal has hashed, so deleting one throws away the evidence of what was sent. A stale frd-completion-runs/<runUuid>/ is the one to look at twice: if a completion was interrupted, that folder is the recovery material.
