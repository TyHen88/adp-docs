Process 7

Delivery channel — where a request goes

A project sends its development requests one of two ways, and the super account picks which. The setting looks like a preference; it behaves like a contract, because the choice is frozen per request at first send and everything afterwards — status, withdrawal, results — follows the frozen one.

What the two sides actually are

Developer connection → the DEVELOPER application

A separate web application the development organisation runs, with its own accounts, its own group management and a work inbox (작업 수신함). It lives in its own repository, we-adk-developer; Builder only ever talks to it over HTTP. This is the intended channel.

GitLab issue link → the development team's tracker

The fallback for a group whose DEVELOPER environment is not ready yet: the request is opened as an issue in the development organisation's GitLab repository, with the ZIP attached.

Neither one is the planning repository

The planning repo and its token are a different registration on the same admin screen. Pointing the issue target at the planning repository would turn the planning team's own repository into somebody else's task list.

And neither is a person

There is no email step and no manual hand-off in either channel. What a human does is press send; everything after that is one of the two machines below.

The screen

Project management → the project → the 개발요청 전송 방식 card → a dialog with one radio pair and two forms behind it. Each radio says whether that side already has its details stored, so you can see which one is ready without opening it. The admin controller is behind hasRole('SUPER'), so only the super account can change a channel.

MethodWhat you typeWhere it posts
Developer connection Developer base URL, Developer group ID — no token POST /admin/projects/{id}/developer-target
GitLab issue link GitLab URL, development repository (group/project), GitLab token POST /admin/projects/{id}/dev-issue-target

Choosing is a side effect of saving

There is no separate apply step. Whichever form you save becomes the method.

01

retire every version → reactivate the matching one, or insert a new version
Re-saving the same URL and group ID reuses the existing version instead of piling up duplicates.
↓
02
Save the GitLab form
store the GitLab target → retire every Developer version
The Developer history is not deleted — switching back later does not mean typing the address again.

Versions, not one overwritable row

adk_builder_developer_target id · project_id · base_url · group_id · current_target · created_at partial unique index — at most one current_target = true per project all of them false ⇒ GitLab is the selected method adk_builder_developer_delivery request_id · target_id · rejection_reason pins the exact version one request was sent with adk_builder_dev_request … · legacy_delivery marks requests that already had GitLab history when these tables landed
Why not just overwrite the row

A request that has already gone out must keep asking the address and group it was actually handed to. Overwriting would silently redirect every in-flight request's status poll, withdrawal and result download to a connection that never received it. The GitLab side needs no versioning for the same reason it needs a token: there is one target per project, and the issue itself carries the identity.

The rule that matters — bound at first send

Every outbound operation asks the same question first, in the same order.

01
Is this request already bound to a Developer version?
send · lookup · withdraw · inspect · results · download
Yes → use that exact version, even if the project setting has changed since.
↓
02
Not bound — does the project have a current Developer connection?
targets.current(projectId)
Yes → bind the request to it now, then send. The binding is what freezes the channel.
↓
03
No current connection → GitLab
falls through to the issue gateway
A request sent as an issue keeps using GitLab afterwards, whatever the setting becomes.

So changing the setting only affects requests that have not been sent yet. That is the whole behavioural difference between this screen and an ordinary preference: switch a project to Developer and yesterday's issues are still read from GitLab; switch it back to GitLab and the requests Developer already accepted are still polled there.

Nothing is verified when you save

The first real send is the test

Registration never calls Developer — the token round-trip was removed on 2026-09-08. Validation is local only: the base URL must parse as http or https (trailing slashes are stripped), and the group ID must be non-blank, whitespace-free and 255 characters or fewer.

This is the opposite of the planning-repository token, which is proven before the row is saved because git ls-remote costs a second (see Project setup). Here there is nothing cheap to call: no auth endpoint, no credential to check. So the cost is deferred to the first send instead of being faked with a request that proves nothing.

How you know it worked

Builder counts a send as complete only when the answer echoes the delivery key back. A wrong host that still answers 200 — a proxy, an SSO login page — leaves the request at “sending” instead of falsely reporting success. On the far side, a successful first intake raises a notification on their admin account reading [DR-005] {title} 접수, linking to /requests/{id}. If you see that, the channel is right.

Developer connection, in detail

Five calls, all against the base URL you registered, all keyed by the delivery key:

CallWhenWhat it carries
POST {base}/intakeSend, and every resendmultipart, eleven fields plus the ZIP, no auth header
POST {base}/intake/withdrawThe planner retractsJSON: groupId, requestNumber, deliveryKey, reason
GET {base}/intake/{deliveryKey}Every 60 s while open→ {deliveryKey, requestNumber, status}
GET {base}/intake/{deliveryKey}/resultsEvery 60 s→ [{id, body, zip}], newest first
GET {base}/intake/{deliveryKey}/results/{id}.zipWhen a result is appliedThe archive — attachment, no auth, host must be the registered one
Only two of those paths are configurable

builder.developer.intake-path (default /intake) and builder.developer.withdrawal-path (default /intake/withdraw), overridable with BUILDER_DEVELOPER_INTAKE_PATH and BUILDER_DEVELOPER_WITHDRAWAL_PATH. The status and result paths are derived from the intake path, so there is nothing separate to misconfigure. Changes need a Builder restart, and the client's per-call timeout is a flat two minutes.

There is no token, so the group ID is the identity

Copy exactly what DEVELOPER's group-management screen shows under 「그룹 ID」. The API contract describes it as a zero-padded seven-digit number and the form's placeholder shows group-001, but the server accepts any non-blank string without spaces, up to 255 characters — so the shape of the hint proves nothing. A group that does not exist over there fails the send with 404, and a delivery key already accepted under a different group fails with 409.

GitLab issue link, in detail

Two calls to send, and then the issue itself is the channel.

01
Upload the ZIP
POST {base}/api/v4/projects/{url-encoded path}/uploads · multipart · PRIVATE-TOKEN
The response's markdown field is the attachment link that goes into the issue body.
↓
02
Open the issue
POST …/issues · title · body carrying the delivery key · labels=intake
GitLab returns the created issue, and our key is in the body it returns — that is the receipt.
↓
03
Status comes from the labels
GET …/issues/{iid} → exactly one of intake · progress · done · rejected
Two state labels at once, or none, reads as unknown and changes nothing.
↓
04
Results come from the comments
GET …/issues/{iid}/notes?per_page=100 → notes tagged [RSLT] <DR number>
Only tagged comments are read, each with one attachment; ordinary discussion is ignored.
LabelMeans
intakeReceived, not yet picked up — and the only state in which a withdrawal is accepted
progressIn development
doneDevelopment complete
rejectedSent back. Not part of the original issue flow — it arrived with the Developer status model
withdrawnNot a state: it records why intake was removed

Withdrawing performs one update — remove intake, add withdrawn, close the issue — and then comments the reason. If that comment fails the withdrawal still stands; only a log line is left.

Duplicate protection only GitLab can offer

Before sending, the gateway searches issues for the delivery key. If one exists, that issue is the answer — which is why pressing send again from “sending” is allowed on this channel. Not zero risk: where GitLab search is backed by Elasticsearch a just-created issue may not be indexed yet, and then a second issue does open. The default database-backed search is immediate.

Two things the client refuses to do

It never follows redirects (Redirect.NEVER): a 302 on a POST becomes a GET that discards the body and returns a cheerful 2xx having sent nothing. And it never enables silent POST retries — Java's client has that off by default, and it stays off.

The GitLab token

Checked at the input field, and only there

It must be printable ASCII. The token rides in the PRIVATE-TOKEN header, so a Korean character or a stray space throws at send time and leaves the attempt frozen in “sending” with no visible cause — the person then asks the receiving side about a problem that was in the text box. It is sealed before storage and never shown back; the screen says only that it is registered, and leaving the field untouched keeps the stored one.

It is deliberately not the clone token

Opening issues is a different permission from cloning a repository, and the two targets are different organisations' property. Keeping them apart means a leak of one does not hand over the other.

With neither configured

The request falls back to a logging gateway: the package is built and left on disk, and the state stays “sending”. It is an escape hatch kept deliberately as a switch — and it is also what makes testing FRD work safe, because with no channel registered nothing can leave the machine.
