Process 8

Sending to development

The package this process bakes is the contract with the development team. That is the standard it is held to: not whether it looks tidy, but whether a missing field leaves something to argue about later.

The pipeline

The button posts to /projects/{projectId}/artifacts/dev-requests/{requestId}/send with the planner's note, the requested completion and deployment dates, and an optional attachment. The request returns immediately; everything below runs on the delivery executor.

01
Claim the attempt
PREPARING · delivery key DRK-0000007 · attachment stored and hashed
An attempt already active for this request is reused, so a double click does not send twice. The stored attachment is re-hashed; a mismatch stops the send.
↓
02
Precheck — the only place the spec checker runs
DevRequestPrecheck.checkForDelivery(view)
One blocking item and the send stops, naming the first one.
↓
03
PACKING — bake the package
DB snapshot + clone (as-is, assets) + git (the commit it started from)
Materials come from three places; the FRD worktree must still exist.
↓
04
ZIP, then record the fingerprint
delivery.zip · sha256 · entry list
The entry list and hash are what answer “what exactly did we send?” later.
↓
05
POST to DEVELOPER, then read the answer carefully
POST {base}/intake · multipart/form-data · no auth header
201 new, 200 the same active request already exists — both echo the delivery key.
The precheck has two layers, and collapsing them breaks it either way

Blocking stops the send; warning lets it through. If everything blocks, a borderline request can never ship. If everything warns, material the developers cannot use goes out inside the contract. The builder does not write its own validator either — the checker shipped inside the planning repo makes the spec judgement, and this class only translates its findings. It runs on send only: running it on every page view made the same screen look different each time the cache expired.

What lands in their hands

DR-003/ ├─ dev-request.md the request itself ├─ expected-back.md what must come back, and in what shape ├─ manifest.json every file, with size and sha256 ├─ attachments/ whatever the planner attached └─ screens/<system>/ ├─ assets/ css · js · images, copied whole └─ <screenId>/ ├─ as-is.html to-be.html ├─ as-is.md to-be.md └─ changes.md why, and what to watch out for

Where each file comes from, and when

Nothing in that tree exists until the send is pressed — the package is assembled at PACKING. But the material in it was made at three earlier moments, and two of the files are not “made” at all.

FileProduced whenRead from at packing time
to-be.htmlThroughout DRAFTING — every draft, chat edit, direct edit and history restoreThe FRD worktree at the delivery-baseline commit
to-be.mdJust before sending; generated if it is not readyThe FRD worktree — a failure here blocks the send
as-is.html · as-is.mdNever produced — it is what was already theregit show <workspaceBaseSha>:<path>, the work-start commit, not the current filesystem
changes.mdAt packingThe screen's change list, its markers and its state cases
assets/At packingcore/<system>/assets in the clone, copied whole
The baseline is verified before a single file is written

The worktree's HEAD must equal the head sha recorded on the request, and git status --porcelain must be empty. Otherwise the package would quietly fold a later edit into a contract that claims a fixed baseline. Pulling as-is from the base commit rather than from disk is the same rule seen from the other end: as-is must be the state before this FRD touched anything, however many times the file has changed since.

Three cases give you less than the full tree. A backend-only FRD or an SRT has no screens/ folder at all. A new screen has no as-is.* — there is nothing at the base commit to show — and its internal tmp-… id is rewritten to the delivery screen id in the copies. A state screen gets no folder of its own: it rides in the parent's folder as to-be-C01.html, with the parent's changes.md table pointing at it, because its as-is and its to-be.md are the parent's text.

One room per attempt — which is why that folder fills up

A delivery does not overwrite the package: it bakes into dev-request-packages/<requestId>-<attemptId>/, holding delivery.zip and the built package/. The journal records that path, its size and its sha256, so “what exactly did we send, on which attempt?” has an answer per attempt rather than one mutable folder. An attempt that fails before it is activated deletes its own room, and a room left behind by a crash is removed at the next boot — but activated attempts accumulate and nothing trims them, so three rooms for one request means that request was sent three times.

Why there is a system level

The mockups are extracted originals that reference ../assets/css/style.css. Put them one level deeper and every style breaks. With a system folder, that relative path resolves by itself — not one character inside the HTML is edited. Editing them would also make the copies impossible to diff against the originals.

Why no skin is chosen

Choosing one would mean rewriting links inside a stored file, and the selecting code would have to hold institution folder names — the moment it does, the builder knows about the source system. The whole asset folder is copied instead, so every institution variant renders, and the manifest records where the assets came from rather than which was picked.

Every name is ASCII

Folders are screen IDs (wv-card-list), files are dev-request.md and changes.md. Korean names in a ZIP depend on the encoding bit and break in older tools; the human-readable screen name lives inside the markdown instead.

Zero screens is valid

A backend-only or fast-track FRD has no screen work at all. A package must be well-formed without a screens/ folder — a check demanding “at least one screen” would mean those requests can never ship.

Nothing may delete the worktree before the send finishes

as-is is the state before the completion commit and to-be is the state after, and both are read out of the same FRD worktree. Remove it early and the material for the contract is gone.

The call itself

FieldWhat it carries
titleThe request title — without the DR number, which travels separately
bodyStructured JSON (we-adp-dev-request/1), not markdown, so DEVELOPER renders the same view without reinterpreting prose. The markdown is still inside the ZIP.
fileThe ZIP as Builder stored it — 20 MB per file, 25 MB per request
requestNumber · workNumber · workTypeDR-005 · FRD-002 or SRT-003 · FRD or SRT

groupIdThe registered DEVELOPER group. There is no token, so this is the connection identity.

The lookup key is the delivery key, not the DR number

DR numbers restart at 1 in every project, so they are not unique on the DEVELOPER side. Resending uses the same delivery key, and the same active request is not created twice — the existing confirmation comes back instead.

Turning an answer into a state

One rule decides everything here: only a proven “they did not take it” becomes NOT_SENT; anything unknown stays SENDING.

AnswerStateWhy
200 / 201, delivery key echoedSENTProof they hold it
200 / 201, nothing echoedSENDINGCorporate proxies and login pages also answer 200
202SENDINGAccepted is not processed
408 · 429SENDING“Not now”, not “no”
409judged, never assumedIt can mean “already received” or a real conflict
NOT_SENT → SENDING → SENT → WITHDRAWN fix it and send again, same key
Withdrawal is not a cancellation

What went out cannot be unsent — a notification was raised and read. Withdrawing tells DEVELOPER, in their own terms, that it is retracted, and it is accepted only while the request is still at INTAKE. It is a separate state, never a return to NOT_SENT: with the request still alive on their side, “not sent” would let someone press send and open a second one.
