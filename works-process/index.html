Work processes

How the work actually moves

Twelve process maps, plus the on-disk layout and a set of samples for exercising them. Each map follows a single action — from the button a person presses to the last thing written to disk or sent over the network — and names, at every step, what fails and what that step is protecting. The narrative reference pages are one level up; these are the diagrams.

End to end

STAGE 1
Set up
A GitLab planning repo is registered, verified and cloned; worktrees are cut from that clone. Nothing downstream exists until this lands.
STAGE 2
Work on an FRD
A typed sentence becomes a scope, the scope becomes screens and documents, and completion closes the work safely. Small changes take the SRT short path instead.
STAGE 3
Hand it over
The request is checked, baked into a package, zipped and sent — to Developer or as a GitLab issue, depending on the channel the project chose.
STAGE 4
Take it back
Status is polled, the returned archive is validated, and a planner decides whether it merges into the default branch.
One work unit, all the way through

FRD 1 = one work item = one git worktree = one person. Every process below is either preparing that worktree, filling it, or emptying it into someone else's hands.

Reading the diagrams

What you seeWhat it means
A numbered rowOne ordered step: a git command, an HTTP call, or a state change
Grey text on the rightWhat that step costs you, or what it protects
Red text on the rightWhat happens when that step fails
A red calloutA trap that has already been hit at least once
A purple calloutA rule that must not be broken

What is not here

Accounts and first login, document intake, the IA publish, screen-ID assignment, the spec checker and notifications are described on the reference pages only. They are covered as mechanisms rather than as an action a person takes, so a process map would repeat the reference page rather than add to it.
