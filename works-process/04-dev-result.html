Process 10

Development result

DEVELOPER has no inbound API into Builder. Nothing is pushed back — Builder asks, on two schedules that both default to every 60 seconds and are configurable. Everything is looked up by the delivery key.

Status, on a timer

01
Ask about every request that is still open
DevelopmentStatusSchedule · fixedDelay 60000 by default
Each request keeps the connection it was sent with, so a re-registered address never orphans an old one.
↓
02
Fold eight statuses into four
WAITING · DEVELOPING · DEVELOPED · REVIEWING → PROGRESS
An unknown code, and WITHDRAWN, map to nothing: the state is left alone and the attempt is recorded as failed.
INTAKE → PROGRESS → DONE or REJECTED both terminal
DONE is not merge approval

An external development status says the work is finished over there. It says nothing about whether the planning repo should change. Nothing merges on a status alone — a person opens the request and presses 개발 결과 반영.

Receiving the archive

01
Poll for a result, fetch the ZIP
DevResultSchedule → DevResultReceiver
Results arrive as items with an id, a body and a ZIP, keyed by the delivery key.
↓
02
Validate before anything is written to disk
≤ 2,000 entries · ≤ 10 MB per file · ≤ 100 MB total · paths and manifest checked
A bad archive is rejected whole. Unpacking first and checking later is how a ZIP writes outside its folder.
↓
03
Check it against what was promised
expected-back.md · testArtifacts · screen components
The request said what must come back; that contract is what the returned files are measured against.

Applying it

01
A synchronous gate decides whether the button may be pressed
result received? · not already merged? → mark RUNNING
Marked before the async work starts, so the screen shows “running” and nobody presses twice.
↓
02
The worker extracts, commits and pushes
DevResultApplyWorker · @Async
Incremental: what came back is applied into the planning repo, not pasted over it.
Why the gate and the worker are different classes

@Async only works through the Spring proxy. With the gate and the async body in one class, the call is a self-invocation, the proxy is bypassed, and the “background” work runs on the request thread — one apply ran for six minutes on nio-8080-exec-2 before this was split (DR-010, 2026-09-11).

Merging into the default branch

The whole merge runs inside the project repository lock, so one project merges one thing at a time.

01
Is this still the current delivery?
generation check · base commit is a 40–64 hex sha
A superseded send is refused: a stale completion must not merge.
↓
02
Fetch both sides into private refs
git fetch … +refs/heads/<default>:refs/builder/dev-request/<id> +refs/heads/<frd branch>:refs/builder/<branch>
Both commits are then verified to exist with cat-file -e.
↓
03
Already an ancestor? Stop here
git merge-base --is-ancestor
Re-pushing an unchanged HEAD would turn a success into a failure the moment the remote moved on.
↓
04
A throwaway worktree at the remote head
worktree remove --force → worktree prune --expire now → worktree add --detach
Left-over workspaces are cleared first; this folder exists only for the merge.
↓
05
Merge, and try to resolve a conflict with Claude
git merge --no-ff --no-edit -m "merge: DR-00x 개발 완료"
If the resolver cannot settle it: merge --abort, the failure is reported, and the state stays where it was.
↓
06
Push, then bring the local clone level
git push <url> HEAD:refs/heads/<default>
Failing to sync the local clone afterwards is itself a failure — the server would keep serving a stale tree.
What survives afterwards

The merge commit is deliberately --no-ff, authored as the builder rather than as a person, so the history shows a completed request rather than an anonymous fast-forward. The FRD branch is kept; only worktrees are removed.
