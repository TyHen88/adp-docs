SRT — the short path

빠른 개발요청 is for changes simple and concrete enough not to need screen design work. Either entry method always ends in a development request, and an SRT never converts into FRD work.

The very call the FRD path uses — which is the whole point of the bridge.
Why the SRT tables look thin

There is no srt_requirement table and there never should be. An SRT's requirements and completion criteria live as ordinary FRD item and note rows keyed by the bridge FRD, so SRT reuses the FRD machinery instead of duplicating it. Facets are written to the bridge FRD too, not to the SRT row.

Five states, four on screen

READY → ANALYZING → COMPLETE or REJECTED FAILED
Screen stateConditionWhat the planner does
분석 중READY or ANALYZINGWait; closing the screen preserves the registration
생성 대기COMPLETEReview, then press 개발요청서 만들기
확인 필요REJECTED or FAILEDRevise a direct SRT; for a thin Flow original, improve it in Flow and register a new one
완료devRequestId is setOpen the development request and review before sending

devRequestId is checked before the analysis state, which is what lets the completed state win. A test pins it: the delivery state does not overwrite the SRT state.

Two guards against double-running, and one against getting stuck

A set of in-flight SRT ids refuses a second request and returns the current status instead. And status() heals itself: if the row says ANALYZING but the id is not in that set, the analysis was lost to a restart or a rejected submission, so it is requested again rather than showing 분석 중 forever. A full executor queue parks the SRT in FAILED with a retry message — never left claimed.

Do not shrink a scope to fit

A change that needs an interview or screen work belongs in an FRD. That is the one misuse the design names explicitly. Note also that updating a direct SRT resets the analysis to READY and clears the bridge FRD's items — and a Flow-registered SRT cannot be edited at all, because the original belongs to Flow.
