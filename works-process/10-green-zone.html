The green zone — generated artifacts

Five keys in the green block of the left menu. Two arrive from development; three Builder generates itself, and all three generated ones read the same material: the screen HTML and screen MD refreshed by the as-is resync, plus the menu tree.

The as-is resync must arrive first

All three generated documents are written from the refreshed as-is material. Without the development result flow, there is nothing to generate from. And the requirements traceability matrix was deleted on the day the green zone opened — do not revive the matrix key.

One shape, three documents

01
A detail screen is opened
/functional-specs · /screen-designs · /user-manual — {systemCode}/{screenId}
Generation is triggered by opening the document, not by a schedule.
↓
02
Is there a current document, and did its inputs change?
STALE_MARGIN 5 min
No change → the existing revision is shown and nothing runs.
↓
03
Claim it and hand off
state = RUNNING → @Async worker → claude with a JSON schema
The schema enforces shape; the reader keeps only the meaning checks.
↓
04
Only a valid result is promoted to a revision
DONE — or FAILED, RETRY_DELAY 2 min, MAX_ATTEMPTS 2
Evidence IDs that do not exist, move targets that do not exist, duplicates: rejected.
Schema first, reader second

Shape rules live in the JSON schema so malformed output fails before it is parsed; the reader only checks meaning. That split is what keeps the reader small — and what makes “this evidence ID exists” a check worth running, since the material is frozen at generation time.

The three, briefly

기능명세서 — feature spec

Not a new artifact type: it is the place that shows the as-is screen MD. It does not re-read the screen list — the solution sweep already walks the index, the MDs and the git history in one cached pass, and reading again would read the same few hundred screens twice. It writes nothing to the planning repository.

화면설계서 — screen design

Only the screen being opened is generated. Playwright Chromium captures the default screen and its variants: up to 40 callouts, viewport 1600 wide, 16,000 px tall at most, 12 MB per capture and 60 MB per bundle, 12 variants. FRD markers are pulled into the document — which is why marker text written in the workbench is worth writing well.

사용자 매뉴얼 — user manual

Model sonnet, at least one step required, titles ≤ 200 characters. The 60,000-character whole-response cap cannot be expressed in the schema, so it lives in the reader beside the evidence check.

States

RUNNING · DONE · FAILED for all three — the manual labels them 만드는 중, 최신, 생성 실패. Until a screen stands, the menu key shows 준비 중.

Full Chromium, not the shell build

Install with --with-deps chromium and without --only-shell. Without full Chromium everything else keeps working and existing revisions stay readable — only new screen-design and user-manual revisions fail, which makes this an easy thing to misdiagnose.
